# triage

A state machine for moving issues through the full issue-lifecycle workflow. Handles triage evaluation, agent brief authoring, grilling sessions, and wontfix documentation — all from a single natural-language invocation.

---

## The problem it solves

Issue trackers fill up with unlabeled, under-specified issues. An AFK agent assigned an under-specified issue will either do nothing, do the wrong thing, or ask clarifying questions in code comments. The triage skill ensures every issue that reaches `ready-for-agent` has a complete, durable specification — an agent brief — that an agent can work from without human intervention.

It also solves the institutional memory problem. Rejected feature requests leave no record of why, so the same idea gets re-proposed repeatedly. The `.out-of-scope/` system captures rejections permanently.

---

## How it works

The skill runs a natural-language interface over a state machine. The maintainer invokes `/triage` and describes what they want in plain English. The agent interprets and acts.

### The state machine

Two category roles: `bug` and `enhancement`.

Five state roles:

| State | Meaning |
|-------|---------|
| `needs-triage` | Maintainer needs to evaluate |
| `needs-info` | Waiting on reporter for more information |
| `ready-for-agent` | Fully specified, AFK-ready |
| `ready-for-human` | Needs human implementation (judgment, external access, design) |
| `wontfix` | Will not be actioned |

Every triaged issue carries exactly one category role and one state role.

Normal flow: unlabeled → `needs-triage` → one of the five states. `needs-info` returns to `needs-triage` when the reporter replies.

### Showing what needs attention

When the maintainer asks "show me what needs my attention," the agent queries the issue tracker and presents three buckets (oldest first):
1. Unlabeled issues (never triaged)
2. Issues with `needs-triage` label
3. Issues with `needs-info` where the reporter has commented since the last triage notes

### Triaging a specific issue

Four steps in order:

**1. Gather context.** Read the full issue, parse prior triage notes, explore the codebase using the domain glossary, check ADRs in the relevant area, and read `.out-of-scope/` for any prior rejection matching this concept.

**2. Recommend.** Tell the maintainer the recommended category and state with reasoning. Include a brief codebase summary relevant to the issue. Wait for direction.

**3. Reproduce (bugs only).** Before grilling, attempt reproduction — read the reporter's steps, trace the code, run tests or commands. Report whether the repro succeeded, failed, or was insufficiently specified. A confirmed repro makes the resulting agent brief much stronger.

**4. Apply the outcome.** Based on the maintainer's decision:
- `ready-for-agent` → post an agent brief (see [AGENT-BRIEF.md](../../../skills/engineering/triage/AGENT-BRIEF.md))
- `ready-for-human` → same structure but note why human implementation is needed
- `needs-info` → post triage notes with what's been established and what's still needed
- `wontfix` (bug) → polite explanation, close
- `wontfix` (enhancement) → write to `.out-of-scope/`, link to it, close

Every comment posted during triage begins with the disclaimer: `> *This was generated by AI during triage.*`

### Quick state override

If the maintainer says "move #42 to ready-for-agent," the agent trusts them and applies the role directly, skipping grilling. If no agent brief was written, the agent asks if the maintainer wants one.

### AGENT-BRIEF.md in detail

The agent brief is the most important output of the triage skill. The file specifies four writing principles:

**Durability over precision.** The issue may sit in `ready-for-agent` for weeks. The codebase will change. Reference behavioral contracts and type names, not file paths or line numbers.

**Behavioral, not procedural.** Describe what the system should do, not how to implement it. "The `SkillConfig` type should accept an optional `schedule` field" is good; "open `src/types/skill.ts` and add a field" is bad.

**Complete acceptance criteria.** The agent needs to know when it's done. Every criterion must be independently verifiable.

**Explicit scope boundaries.** State what is out of scope. This prevents gold-plating.

The file includes two complete good examples (a bug brief and an enhancement brief) and one bad example annotated with what makes it bad. The contrast is the primary teaching tool.

### OUT-OF-SCOPE.md in detail

The `.out-of-scope/` directory stores rejected feature requests as concept-level Markdown files. One file per concept (not per issue) — multiple issues requesting the same thing are grouped under one file.

The file format is "readable design document" style — paragraphs, code samples, plain English explanation. The goal is for someone encountering the concept fresh to understand not just the decision but the reasoning.

During triage, all `.out-of-scope/` files are checked by concept similarity (not keyword matching). "night theme" matches `dark-mode.md`.

## Mechanism

The skill's effectiveness comes from four design choices:

**Natural language over forms.** The maintainer can say "show me what needs attention" or "move #42 to ready-for-agent" in plain English. The agent interprets these and maps them to state machine operations, making triage fast rather than ceremonious.

**Reproduction before grilling.** Bugs are reproduced before the grilling session starts. This is a strong ordering choice — a confirmed repro means the grilling session is grounded in evidence, not speculation.

**Grilling integration.** For issues that need fleshing out, the skill calls `/grill-with-docs` inline. This connects the triage workflow to the domain documentation workflow — grilling during triage can update `CONTEXT.md` and add ADRs, not just fill out the issue.

**Permanent rejection records.** The `.out-of-scope/` system solves the re-proposal problem. Instead of closed-issue comments that are hard to find, rejection decisions live in a versioned, searchable directory that the skill actively checks at the start of every triage session.

## How to improve

**Add a state machine diagram.** The five states and their transitions are described in prose. A visual diagram (even ASCII) would make the allowed transitions immediately clear, including the `needs-info` → `needs-triage` return path that's easy to miss.

**Clarify "reporter activity" for the third bucket.** The skill says to show `needs-info` issues "with reporter activity since the last triage notes" but doesn't define what counts as reporter activity. Comments from the reporter? Label changes? Clarifying this prevents the agent from either missing relevant activity or showing false positives.

**Add guidance on duplicate issues during triage.** What should happen when two issues in the tracker describe the same bug? Close one with a reference to the other? The skill handles the `.out-of-scope/` deduplication case but not in-flight duplicates.

**Add the category split for wontfix more prominently.** The `wontfix` handling is different for bugs (polite explanation, close) and enhancements (write to `.out-of-scope/`, link, close). This distinction is buried in the "Apply the outcome" list. A prominent note at the `wontfix` state definition would prevent the agent from applying enhancement handling to bugs.
